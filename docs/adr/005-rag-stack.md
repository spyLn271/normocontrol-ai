# 005. RAG: свой код + Qdrant

Статус: принято (2026-10-25)

## Вопрос: нужен ли фреймворк?

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Свой код** (~450 строк: чанкинг, индексация, поиск, оценка) | прозрачно, легко отлаживать, нужный нам чанкинг по пунктам, метаданные и фильтры | писать самим |
| LlamaIndex / LangChain / Haystack | готовые загрузчики | тяжёлые зависимости, абстракции мешают «чанк = пункт стандарта», сложнее защищаться от галлюцинаций |

## Векторная БД

| Вариант | Решение |
|---|---|
| Chroma | не берём: отдельная зависимость только для разработки |
| **Qdrant** | одна реализация на всё: встроенный режим (`vector_store.path`) для разработки и тестов (`:memory:`), сервер (`vector_store.url`) в продакшене; фильтры по `source` |
| LanceDB, pgvector, FAISS | запасные варианты, интерфейс `VectorStore` позволяет добавить |

## Решение

* Извлечение текста: `pypdfium2` (PDF), python-docx (DOCX), TXT/MD; удаление
  повторяющихся колонтитулов («Источник: ИС ПАРАГРАФ…» на каждой странице).
* Чанкинг по пунктам (`rag/chunking.py`): номер принимается, только если он продолжает
  нумерацию (1 → 2, 6.1 → 6.1.1); строки оглавления выкидываются; «Глава N» — родительский
  заголовок и допускает перезапуск нумерации; приложения — отдельные чанки (`kind: appendix`,
  там образцы оформления); длинные пункты режутся по предложениям с перекрытием.
* Идемпотентная индексация: точки источника удаляются, id точек — детерминированный UUID5.
* Поиск: эмбеддинг запроса → top-20 с фильтром по `profile.rag_sources` → (reranker) →
  бонус приоритета источника (методичка вуза важнее ГОСТа).
* Оценка: `normocontrol rag eval` — Hit@k и MRR.
