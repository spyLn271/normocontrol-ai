# 003. Рантайм локальной LLM

Статус: принято (2026-10-25)

## Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Ollama** | одна команда, Docker-образ, JSON Schema в `format`, эмбеддинги тем же сервером, CPU и GPU | меньше пропускная способность при большой нагрузке |
| vLLM | лучшая пропускная способность на GPU, continuous batching | только GPU, сложнее |
| llama.cpp server | лёгкий, GGUF | меньше удобств |
| LM Studio | GUI | не для сервера |
| HF Transformers | гибкость | всё делать самим |

## Эксперимент

Ollama 0.40.2 в Docker на CPU (48 ядер, без GPU): `qwen3:4b` проверяет 8 записей литературы
(2 запроса по 5/3 записи) за ~60 с; `bge-m3` индексирует 411 чанков за 47 с.
Строгий JSON по схеме — 100 % валидных ответов в прогоне.

## Решение

* По умолчанию — **Ollama** (`llm.provider: ollama`): `/api/chat` с `format` = JSON Schema,
  `think: false`, `temperature: 0.1`, `keep_alive`.
* Второй провайдер — **OpenAI-совместимый** (`openai_compatible`): vLLM, llama.cpp server
  и (если клиент разрешил) облачные API. Код проверок не меняется.
* Надёжность: повтор при 5xx/сетевых ошибках (tenacity, экспоненциальная пауза),
  повтор при невалидном JSON (`llm.max_retries`), семафор параллелизма, LRU-кэш ответов.
* Логи промптов (`llm.log_dir`) выключены по умолчанию — в них фрагменты документов.

## Последствия

Переход на vLLM при росте нагрузки — смена `provider` и `base_url` в конфиге.
