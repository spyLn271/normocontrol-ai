# RAG в проекте: как ИИ «знает» ГОСТы и методички

> **Реализовано** (`src/normocontrol/rag/`, ADR 005): извлечение текста PDF/DOCX с удалением
> колонтитулов, чанкинг по пунктам, `bge-m3` через Ollama, Qdrant, фильтр и приоритеты по профилю,
> опциональный reranker, оценка Hit@k/MRR. На Правилах № 236 и МИ 049-2026: **Hit@5 = 0.981**
> ([замер](benchmarks/2026-10-25-rag.md)).

## Зачем нам RAG

LLM не знает точного текста ГОСТ 7.32 или методички конкретного вуза, а если «знает», то неточно.
Если спросить модель без источника, она выдумает правило. RAG решает это так: перед каждой ИИ-проверкой
мы **находим нужный пункт настоящего документа** и кладём его в промпт.

RAG у нас решает **три задачи**:

| # | Задача | Пример |
|---|---|---|
| 1 | Подсказать LLM нужное правило во время проверки | проверяем запись литературы → достаём пункты ГОСТ 7.1 про книги/статьи/электронные ресурсы |
| 2 | Ссылаться на источник в отчёте | «Ошибка: … Основание: ГОСТ 7.32-2017, п. 6.2.1» с цитатой |
| 3 | Помогать создавать профили | загрузили новую методичку вуза → RAG + LLM предлагают черновик YAML-профиля, человек проверяет |

**Чего RAG НЕ делает:** не измеряет поля и шрифты. Это по-прежнему делает код (Rule Engine).

## Схема

```
ИНДЕКСАЦИЯ (один раз на каждый стандарт / методичку)

 PDF/DOCX стандарта ─► [Docling / PyMuPDF] ─► чистый текст с номерами пунктов
                                                │
                                                ▼
                                   [Чанкинг по пунктам: 6.1, 6.1.1 ...]
                                                │
                                                ▼
                                   [bge-m3] ─► векторы ─► [Chroma / Qdrant]
                                                          + метаданные:
                                                          source, clause, title,
                                                          doc_type, jurisdiction, year

ПОИСК (на каждую ИИ-проверку)

 фрагмент документа + тип проверки ─► запрос ─► [bge-m3] ─► top-20 чанков
                                                               │ фильтр по профилю
                                                               ▼
                                                    [reranker] ─► top-3..5
                                                               │
                                                               ▼
                                              промпт: ПРАВИЛА + ФРАГМЕНТ + JSON-схема
                                                               │
                                                               ▼
                                                     [qwen3] ─► JSON с ошибками
                                                               │
                                                               ▼
                                          валидация: есть цитата правила и paragraph_id?
```

## Чанкинг — самое важное

Плохой чанкинг = плохой RAG. Стандарты имеют чёткую структуру пунктов — **режем по ней**, а не по N символов.

- Один чанк = один пункт (`6.1.1`) вместе с заголовком родительского раздела (`6.1 Общие требования`).
- Если пункт очень длинный (> 800 токенов), режем на части с перекрытием 50–100 токенов, номер пункта сохраняем в каждой части.
- Таблицы и примеры (особенно примеры библиографических записей!) — отдельные чанки с пометкой `kind: example`.
- В метаданных обязательно: `source` («ГОСТ 7.32-2017»), `clause` («6.1.1»), `year`, `jurisdiction` (`KZ`, `university:<код>`), `doc_type`.

Пример чанка:
```json
{
  "id": "gost-7.32-2017#6.1.1",
  "text": "6.1 Общие требования\n6.1.1 Изложение текста и оформление отчёта ...",
  "metadata": {
    "source": "ГОСТ 7.32-2017",
    "clause": "6.1.1",
    "jurisdiction": "KZ",
    "doc_type": ["report", "coursework", "thesis"],
    "kind": "rule"
  }
}
```

## Фильтрация по профилю

Методичка вуза может противоречить ГОСТу (например, другие поля). Поэтому поиск всегда
**фильтруется по источникам текущего профиля**, а у методички приоритет выше, чем у базового ГОСТа.
В профиле это описывается так:
```yaml
rag_sources:
  - {source: "Методичка вуза X, 2025", priority: 1}
  - {source: "ГОСТ 7.32-2017", priority: 2}
```

## Промпт (шаблон)

```
SYSTEM:
Ты — нормоконтролёр. Проверяешь фрагмент документа ТОЛЬКО по приведённым правилам.
Если правило не приведено — не придумывай его. Отвечай строго JSON по схеме.

USER:
ПРАВИЛА:
[1] ГОСТ 7.1-2003, п. 5.2: <текст пункта>
[2] ...

ФРАГМЕНТ (paragraph_id=p-311):
"Иванов И.И. Основы программирования. М.: Наука, 2020. 300с."

Найди нарушения. Для каждого укажи rule_ref (номер из ПРАВИЛ), цитату нарушения, как исправить.
Если нарушений нет — верни пустой список.
```

## Защита от галлюцинаций (обязательно)

1. `temperature: 0`–`0.1`.
2. JSON-схема через параметр `format` в Ollama; невалидный JSON → повтор максимум 2 раза → иначе пропуск с логом.
3. Каждая ошибка должна ссылаться на `rule_ref`, который реально был в промпте. Нет — выбрасываем.
4. Цитата из фрагмента должна реально в нём находиться (проверяем подстрокой). Нет — выбрасываем.
5. Исправление (`fix`) обязано отличаться от исходного текста, а запись, совпадающая с образцом
   из найденного официального текста, ошибкой не считается.
6. Логируем запросы и ответы в `logs/llm/` (`llm.log_dir`) — по ним улучшаем промпты. По умолчанию
   выключено: в логах фрагменты документов (персональные данные).

## Как оценивать RAG

Отдельно от всей системы, на маленьком наборе вопросов (`tests/rag/questions.yaml`):
```yaml
- query: "оформление электронного ресурса в списке литературы"
  expected_clauses: ["ГОСТ 7.1-2003#…"]
```
Метрики: **Hit@5** (нужный пункт есть в top-5) и **MRR**. Цель MVP: Hit@5 ≥ 0.9.
Сравниваем: bge-m3 vs qwen3-embedding, с reranker и без, разные размеры чанков.

## Тексты стандартов и авторские права

Тексты ГОСТов и методичек **не кладём в публичный доступ**. В репозитории — только скрипты загрузки
и индексации, сами файлы лежат в `data/standards/` (папка в `.gitignore`). Перед продакшеном проверить
условия использования каждого источника (см. [RESEARCH.md](RESEARCH.md)).
