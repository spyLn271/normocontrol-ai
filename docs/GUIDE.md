## 1. Что мы строим — в одном абзаце

Человек загружает документ (курсовую, диплом, служебную записку). Программа читает файл,
**кодом** проверяет то, что можно измерить (поля, шрифт, интервалы, отступы), а **локальной ИИ-моделью**
проверяет то, что требует понимания текста (оформлен ли список литературы по ГОСТу, правильно ли
подписаны рисунки, все ли поля шаблона заполнены). Чтобы ИИ не выдумывал требования, мы даём ему
**текст настоящих стандартов** через RAG. На выходе — отчёт: «ошибка — где — как исправить».

## 2. Почему не «просто спросить ChatGPT»

Важно понять это с самого начала, иначе проект превратится в обёртку над чатом, которая врёт.

| Проблема | Почему это плохо | Как решаем |
|---|---|---|
| LLM не видит форматирование | когда текст из .docx отдают модели, теряются поля, шрифты, отступы — модель их просто *угадывает* | эти параметры достаём парсером и проверяем кодом |
| LLM плохо считает | «интервал 1,15 или 1,5?» — модель может ошибиться | числа сравнивает код |
| LLM выдумывает правила | «по ГОСТу шрифт 13» — уверенно и неправда | RAG: даём модели реальный текст пункта стандарта и требуем ссылку на него |
| Документы содержат личные данные | ФИО, ИИН, адреса нельзя слать в чужие облака | **локальная модель** — данные не уходят с компьютера/сервера |
| Стоимость | облачные API стоят денег за каждый запрос | локальная модель бесплатна после скачивания |

**Правило проекта:** если что-то можно проверить кодом — проверяем кодом. ИИ — только там, где без него никак.

## 3. Словарь (обязательно прочитать)

**LLM (Large Language Model)** — большая языковая модель. Программа, которая по тексту-вопросу
генерирует текст-ответ. Примеры: Qwen, Llama, Gemma, Mistral, GPT, Claude.

**Локальная модель** — LLM, которая скачана на твой компьютер и работает без интернета.
Файл модели весит от 2 до 40+ ГБ.

**Параметры (7B, 14B, 32B)** — «размер мозга» модели в миллиардах. Больше — умнее, но медленнее
и требует больше памяти. Для нас разумный диапазон 4B–14B.

**Квантизация (Q4, Q5, Q8)** — сжатие модели. `Q4_K_M` занимает примерно в 4 раза меньше памяти,
чем оригинал, и почти не теряет в качестве. Почти всегда используем Q4_K_M или Q5_K_M.

**Ollama** — программа, которая скачивает и запускает локальные модели одной командой
(`ollama run qwen3:8b`) и даёт к ним HTTP API на `http://localhost:11434`. Наш основной инструмент.

**Контекстное окно** — сколько текста модель может «держать в голове» за раз (в токенах).
Токен ≈ 3–4 символа для русского. Диплом на 60 страниц целиком не влезет в маленькую модель —
поэтому мы режем документ на куски.

**Промпт** — текст инструкции, который мы отправляем модели. **System prompt** — постоянная
инструкция «кто ты и как отвечать», **user prompt** — конкретный запрос.

**Structured output / JSON mode** — режим, когда модель обязана ответить валидным JSON по нашей схеме.
Без этого ответ модели невозможно надёжно обработать кодом. В Ollama — параметр `format` с JSON-схемой.

**Температура** — «случайность» ответа. Для проверок ставим `0`–`0.2`: нам нужна повторяемость, а не творчество.

**Эмбеддинг (embedding)** — превращение текста в вектор (список чисел, например 1024 числа).
Похожие по смыслу тексты дают близкие векторы. «Список литературы» и «Список использованных источников»
будут рядом, хотя слова разные.

**Модель эмбеддингов** — отдельная небольшая модель (не LLM), которая только делает векторы.
Быстрая, лёгкая (0.5–2 ГБ).

**Векторная база данных** — база, где хранятся векторы и которая умеет быстро искать «ближайшие»
к запросу. Примеры: Qdrant, Chroma, LanceDB, pgvector.

**RAG (Retrieval-Augmented Generation)** — «генерация с подсказкой из базы знаний».
1) Нарезаем ГОСТы на кусочки и сохраняем их эмбеддинги. 2) Когда надо проверить, например,
список литературы, ищем самые подходящие кусочки ГОСТа. 3) Кладём их в промпт:
«Вот правила: …. Проверь запись: …». Модель отвечает, опираясь на реальный текст.

**Чанк (chunk)** — кусок текста, на который режем документ для RAG (обычно 300–800 токенов).

**Reranker** — модель, которая из, скажем, 20 найденных чанков выбирает 3–5 действительно
релевантных. Сильно повышает качество RAG.

**Галлюцинация** — когда модель уверенно говорит неправду. Наша главная угроза.

**Precision / Recall** — метрики качества.
Precision — какая доля найденных нами ошибок *настоящие*. Recall — какую долю *всех* настоящих ошибок мы нашли.

**Fixture / эталонный документ** — тестовый `.docx`, в котором мы заранее знаем все ошибки.

## 4. Что установить

> Ниже команды для Windows. На macOS/Linux всё то же, но через терминал и `brew`/`apt`.

### 4.1. Базовые инструменты
| Инструмент | Зачем | Как проверить |
|---|---|---|
| [Git](https://git-scm.com/) | контроль версий | `git --version` |
| [GitHub CLI](https://cli.github.com/) | PR и Issues из терминала | `gh --version`, затем `gh auth login` |
| [Python 3.12](https://www.python.org/) | основной язык | `python --version` |
| [uv](https://docs.astral.sh/uv/) | менеджер пакетов и виртуальных окружений (быстрее pip) | `uv --version` |
| [VS Code](https://code.visualstudio.com/) или PyCharm | редактор | — |
| [Docker Desktop](https://www.docker.com/products/docker-desktop/) | запуск Qdrant и деплой | `docker --version` |
| [LibreOffice](https://www.libreoffice.org/) | конвертация .docx → .pdf (для номеров страниц) | `soffice --version` |

Расширения VS Code: Python, Pylance, Ruff, GitLens, YAML.

### 4.2. Ollama и модели
1. Скачай и установи Ollama: https://ollama.com/download
2. Проверь: `ollama --version`
3. Скачай модели (подробно, какие и почему — в [MODELS.md](MODELS.md)):
   ```
   ollama pull qwen3:8b
   ollama pull bge-m3
   ```
4. Проверь чат: `ollama run qwen3:8b "Сколько будет 2+2? Ответь одним числом."`
5. Проверь API:
   ```
   curl http://localhost:11434/api/tags
   ```

### 4.3. Запуск проекта

```bash
git clone <адрес репозитория> && cd normocontrol-ai
make install                                   # = uv sync --extra pdf + pre-commit install
uv run normocontrol check file.docx --profile kru-mi-049-2026 --no-llm
make check                                     # линтер, типы, тесты — как в CI
```

Без Ollama работает всё, кроме ИИ-проверки списка литературы (в отчёте будет пометка).
Для номеров страниц нужен LibreOffice Writer (`soffice`); без него страницы оцениваются приблизительно.

### 4.4. Сколько нужно железа
| Конфигурация | Что потянет |
|---|---|
| Ноутбук без видеокарты, 16 ГБ ОЗУ | модели 4B–8B в Q4, медленно (5–15 токенов/сек), для разработки достаточно |
| Видеокарта NVIDIA 8 ГБ | 8B в Q4 — комфортно |
| Видеокарта 12–16 ГБ | 14B в Q4 — хорошо |
| 24 ГБ+ | 32B в Q4 — отлично, это уровень для продакшена |

Если компьютер слабый — разрабатывай на маленькой модели (`qwen3:4b`), качество потом сравним на более сильной.

## 5. Как работать с Git (минимум)

```bash
git clone https://github.com/taaazhi/normocontrol-ai.git
cd normocontrol-ai

git checkout -b feat/parser-margins     # новая ветка под задачу
# ... пишешь код ...
git add .
git commit -m "feat(parser): read section margins"
git push -u origin feat/parser-margins

gh pr create --fill                      # открыть Pull Request
```

Правила:
- **одна задача = одна ветка = один PR**;
- PR маленькие (до ~400 строк), большие задачи режь на части;
- в описании PR: что сделано, как проверить, `Closes #<номер Issue>`;
- в `main` напрямую не пушим.

Подробнее о процессе — [CONTRIBUTING.md](../CONTRIBUTING.md).

## 6. Как работать с ИИ-ассистентами при разработке

Пользоваться Claude / ChatGPT / Copilot для написания кода — **можно и нужно**, но:
- не копируй код, который не понимаешь. Если не можешь объяснить строчку — спроси ассистента, что она делает;
- всегда запускай тесты после вставки сгенерированного кода;
- требования ГОСТа у ассистента не спрашивай — он их выдумает. Только из оригинального текста стандарта.
